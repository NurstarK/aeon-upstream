# ISS-003 — Scheduler dispatching intermittently

## Summary
Enabled skills are not running on their declared schedules. `heartbeat` is the
canary: it is scheduled 3× daily (08:00 / 14:00 / 20:00 UTC) but recorded no
successful run across multiple consecutive slots. Because heartbeat is the skill
that writes the public status page and runs fleet health checks, a stalled
scheduler means the whole fleet goes unmonitored and `docs/status.md` goes stale
without anyone being alerted.

## Evidence
- 2026-10-14 20:48 heartbeat run: self-check FIRED — `last_success` was
  2026-10-10T14:42:56Z (~98h, >36h). Status page 4 days stale. Flagged as a
  possible scheduler stall; folded into the notification; no ISS filed yet
  ("may warrant a new ISS if it recurs").
- 2026-10-16 14:49 heartbeat run: self-check FIRED AGAIN — `last_success`
  2026-10-14T20:49:40Z (~42h, >36h). No log exists for 2026-10-15 at all; the
  10-15 08:00/14:00/20:00 and 10-16 08:00 scheduled heartbeat slots did not
  report back. **Recurrence confirmed** → issue filed.
- Downstream staleness this is the root cause of: `autoresearch` last success
  2026-10-12T07:28 (>48h for a daily skill); `agent-buzz` last success
  2026-10-13T18:17 (>48h). Both repeatedly flagged stale by heartbeat P3.
- 2026-10-17 21:06 heartbeat run (20:00 slot, fired ~1h late): self-check now
  OK (`last_success` 2026-10-16T21:32:53Z, ~23.5h, <36h). BUT intermittent
  dispatch persists — today's **10-17 08:00 and 14:00 heartbeat slots never
  fired** (heartbeat `last_dispatch` still 2026-10-16T21:30:41Z before this
  run). The **07:00 autoresearch slot remains dead since 2026-10-12**
  (`last_dispatch` 2026-10-12T07:27:32Z, now ~5 days) — the single most
  persistent gap. agent-buzz 17:30 slot did fire (last_dispatch
  2026-10-17T18:52:29Z). Pattern unchanged from 10-16: evening slots recover,
  morning/midday slots (esp. 07:00) are the ones dropped.

## Impact
- Fleet health checks and the public status page only update when a human-less
  cron actually fires. Intermittent dispatch means `docs/status.md` can be days
  stale while showing a green-looking skill table (cron-state records exit-success
  per run, so skills look healthy at the scheduler level).
- Distinct from ISS-001 (autoresearch misconfig) and ISS-002 (agent-buzz missing
  secret): those skills fail/no-op *when run*; ISS-003 is that they are not being
  *run* on cadence in the first place.

## Fix options
1. Inspect the GitHub Actions scheduled-workflow run history (`gh run list` /
   Actions UI) to confirm whether cron triggers are firing. GitHub disables
   scheduled workflows on repos with no recent commit activity for ~60 days and
   can throttle `schedule:` events under load — verify neither applies.
2. If the schedule workflow is disabled/throttled: re-enable it, and/or add a
   lightweight keepalive commit or `workflow_dispatch` recovery path.
3. Verify the cron workflow YAML's `schedule:` block is valid and the workflow
   file is on the default branch (schedules only run from the default branch).
